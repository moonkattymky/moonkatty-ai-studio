## QA-NODE-001 … 006

Пол QA-NODE-001 сравнивает метку подписи со временем создания менеджера. Запрос, пойманный до перезапуска, новый процесс отвергает, даже если карта nonce пуста и окно ±30 с ещё открыто. Метка ровно на 1 мс раньше старта тоже даёт `E_REPLAY`.

Остаток: окно симметричное. Подпись с меткой «сейчас + 25 с» первый процесс принимает. Второй процесс, стартовавший на 1 с позже, видит ту же метку всё ещё впереди и не ниже своего старта, карты nonce у него нет, и подпись проходит снова. Для обычного запроса с меткой «сейчас» перезапуск по-прежнему закрыт.

QA-NODE-002. `peerOf` при `trustServeHeaders: false` на сокете `127.0.0.1` возвращает ключ `loopback`, даже если в запросе есть tailnet-адрес и `Tailscale-User-Login`. `nodes-server.js` ставит флаг только при точной строке `STUDIO_NODES_TRUST_SERVE=1`. С флагом тот же заголовок получает ключ `tsnode:victim`. Потоп зачислений с ключом `loopback` доводит корзину до `E_IP_LOCKED` и не мешает зачислению с ключом `tsnode:victim`. Это и есть заявленный остаток: локальные неопознанные клиенты делят одну корзину, и один из них может запереть остальных на 15 минут.

QA-NODE-003 проверен на живом `server.js` со flavor `test`, отдельным каталогом данных и поддельным паролем. Отклонение до pending уже режется словом и паролем. После зачисления устройства по закреплённому TLS отказ с паролем и словом `ОТКЛОНИТЬ` переводит запрос в `rejected`.

QA-NODE-004. Лимит верного опроса отдельный, 60 в минуту на запрос. Лимит плохих секретов на peer сохранён. Клиент `enroll.js` после ответа 429 `E_RATE_LIMIT` делает паузу около 5 с и продолжает опрос. Замер на локальном TLS-макете: второй status ушёл через 5–9 с.

QA-NODE-005. `PUT /api/nodes/files/<sha256>` подписывается hash потока. Совпадение даёт 200 и файл по адресу hash. Несовпадение hash URL и тела даёт 422. Подпись пустого тела при непустом теле даёт 401. Каталог после отказов не содержит `up.*.tmp`.

QA-NODE-006. `enrolledAgentOk` требует major 0, minor 2, patch не ниже 2. Диапазон в ответе для подключённого узла: `>=0.2.2 <0.3.0`. Рекламируемый `AGENT_RANGE` для legacy остаётся `>=0.2.0 <0.3.0`. Суффикс `0.2.2-rc.1` тем же регулярным выражением принимается. Жёсткий затвор протокола по-прежнему nonce и подпись ключа устройства. Прямые токены 0.2.0 на HTTP выключены.

## Безопасность узла

Зачисление по коду само токен не выдаёт. Токен появляется один раз после подтверждения владельца и подписанного status. В `nodes.json` лежат hash токена и hash кода. Журнал аудита секрет зачисления не пишет.

Слушатель Node API отказывается от LAN и публичных адресов. Панель при `HOST=0.0.0.0` в наборе `test:nodes` завершается с кодом 78. Настройки отвергают привязку к `0.0.0.0`, `192.168.1.5`, `10.0.0.2`, `8.8.8.8` и `127.0.0.1`. Адрес Tailscale `100.101.102.103` настройка принимает и требует перезапуск. Этот адрес здесь не поднимался.

`getUrl` не ходит по редиректу и не открывает `file:`. Обработчики зовут `execFile` со списком аргументов. Заглушка `sips` получила имя `evil;id` одним аргументом и format `jpeg`. Настоящий `sips` и `ditto` на Linux отсутствуют: исполнение этих команд BLOCKED, отказ `image.light` без бинарника в коде есть.

`telegram.notify` и `notify.send` вызывают одну функцию `localNotify`. Тело уходит на URL из `NODE_NTFY_URL`. Подмена через поле задания не срабатывает. Это ntfy, не Telegram Bot API. В тестах разработчика тот же путь закрыт локальным TLS-макетом.

## Что не мешает чтению FAIL

Реальные Mac, живой Tailscale, Gatekeeper, launchd и настоящая Связка ключей не проверялись. Это BLOCKED, не повод для FAIL.
